# Avatar

The VRM avatar system: what the loader reads from a VRM file, the humanoid bone table and its version differences, the rest skeleton derived from it, the MToon subset the renderer implements, the retarget that poses the avatar from the tracked frame, the per-avatar rig settings that correct the mapping and the retarget's assumptions, the avatar-driven VMC output, and the panel that drives it. See [conventions.md](./conventions.md) for the avatar space and its single conversion point, [architecture.md](./architecture.md) for where the modules sit, and [testing.md](./testing.md) for the tests.

External references, both public: the VRM specification (https://github.com/vrm-c/vrm-specification), including `VRMC_vrm-1.0`, the `VRM` 0.x extension, and `VRMC_materials_mtoon-1.0`, and the pixiv three-vrm renderer (https://github.com/pixiv/three-vrm), whose VRM 0.x material migration the loader follows.

---

## Files and the two VRM generations

A VRM is a glTF 2.0 binary (`.vrm` is a `.glb`) plus one top-level extension that names which glTF node plays which humanoid bone and carries the metadata. Two generations exist and both load into one `AvatarModel`:

- VRM 0.x: extension `VRM`, `specVersion` "0.0", exported by UniVRM 0.x and VRoid Studio. The model faces glTF -Z with its left at -X. Humanoid bones are an array of `{bone, node}` in Unity `HumanBodyBones` spelling. Materials are a Unity property bag per material (`materialProperties[]`).
- VRM 1.0: extension `VRMC_vrm`, `specVersion` "1.0". The model faces glTF +Z with its left at +X. Humanoid bones are an object keyed by bone name, with the thumb renamed to metacarpal/proximal/distal. MToon lives in a per-material `VRMC_materials_mtoon` extension.

When a file carries both extensions, `VRMC_vrm` wins. Everything version-specific is resolved in `VrmLoader` and `AvatarSkeleton`; nothing downstream branches on the generation.

The CC0 VRoid Studio samples `models/avatars/fem_vroid.vrm` and `masc_vroid.vrm` (fetched by `InitialSetup_x64.bat`, provenance in `NOTICE.md`) are VRM 0.x. A VRM 1.0 file is covered by the synthetic test only until a redistributable 1.0 sample is added.

## The loader (`src/Avatar/VrmLoader.h`)

`VrmLoader::loadFile` and `loadMemory` produce an `AvatarModel` (`src/Avatar/AvatarTypes.h`) or an error string, plus non-fatal warnings. Pure CPU work with no GL and no app state, so the self test runs it on an in-memory file and `--vrm-info` on any path. The glTF core goes through `cgltf` (`thirdparty/cgltf`, one `CGLTF_IMPLEMENTATION` in `VrmLoader.cpp`): parse, load the embedded buffers, validate, then read through `cgltf_accessor_read_float` / `read_uint` / `read_index`, which resolve normalized, strided, and sparse accessors. The VRM extension JSON is read directly with nlohmann for the subset the app uses. What lands in the model:

- nodes: name, parent, children, the parent-relative local transform as authored (TRS composed, or the matrix as given), mesh and skin indices
- skins: joint node indices and inverse bind matrices (identity when absent)
- meshes: triangle primitives only, with positions, normals (empty when absent), `TEXCOORD_0`, `JOINTS_0` as `uvec4`, `WEIGHTS_0` renormalized to sum one, and `uint32` indices (generated when the file has none)
- materials: base color factor and texture, alpha mode, alpha cutoff (default 0.5), double sided, and the MToon subset (below)
- textures and images: wrap and filter flags per texture, and every image decoded through `cv::imdecode` to RGBA8 with rows kept top-down (glTF's UV origin is the top-left texel, which is also the first row GL receives, so nothing flips anywhere); an undecodable image becomes a 1x1 white placeholder with a warning
- the humanoid map: one node index per `eHumanoidBone`, -1 when absent, kept twice: `fileHumanoidNodes` as the file names it and `humanoidNodes` as in effect after the rig settings' overrides
- meta: name, version, author, license (1.0 `licenseUrl`, 0.x `licenseName`)
- morph target names per mesh (glTF `extras.targetNames`, the index as a string when absent), and per primitive each target's position and normal offsets kept sparse, only the vertices it moves
- expressions: each `AvatarExpression` has the name as the file spells it, a VRM 1.0 preset name (0.x `presetName` values are mapped onto that vocabulary, an unknown preset is empty like a custom expression), `isBinary`, and morph binds of `(mesh, morphIndex, weight)` with weight 0..1. 0.x reads `blendShapeMaster.blendShapeGroups` (mesh index in the bind, weight divided by 100), 1.0 reads `expressions.preset` and `expressions.custom` (node index in the bind, resolved to the node's mesh). Binds out of range warn and are dropped. Material color and texture transform binds are ignored. `findExpressionByPreset` and `findExpressionByName` look them up
- `sha256Hex`: SHA-256 of the exact file bytes (Windows CNG), computed for memory loads too

A load fails when the glTF is invalid, when neither VRM extension is present, or when a required humanoid bone is missing (hips, spine, head, both arms with hands, both legs with feet). Unknown bone names warn and are ignored.

## The humanoid table (`eHumanoidBone`)

The 55 VRM humanoid bones in Unity `HumanBodyBones` vocabulary, the spelling VMC receivers and the 0.x extension both use, so `humanoidBoneName` matches `VmcRetarget::boneName`. Fingers are laid out as 3 bones x 5 fingers x 2 hands in app finger order (thumb, index, middle, ring, little), proximal first, so a `(side, finger, phalanx)` triple indexes as `firstHumanoidFingerBone(side) + finger * 3 + phalanx`.

The VRM 1.0 thumb rename is folded back into this table: 1.0 `thumbMetacarpal` maps to `ThumbProximal` and 1.0 `thumbProximal` to `ThumbIntermediate`. The app's thumb phalanx [0] is the metacarpal (`FINGER_JOINTS` thumb `{CMC, MCP, IP, TIP}`), so app thumb proximal = 1.0 metacarpal = 0.x proximal, and the three thumb slots line up with the three app phalanges like every other finger.

`humanoidBoneParent` is the spec hierarchy. Optional bones (upper chest, shoulders, toes, eyes, jaw, all fingers) may be absent, so `AvatarSkeleton` resolves each bone's nearest PRESENT ancestor instead (an avatar without an upper chest hangs its neck and shoulders off the chest).

## The rest skeleton (`src/Avatar/AvatarSkeleton.h`)

`AvatarSkeleton` is immutable rest-pose data derived from a model, in the app's world frame, built once on load and shared by pointer. Everything comes from composed rest WORLD transforms, never from node-local rotations: a VRM 1.0 rig is not required to be normalized (nodes may carry rest rotations), and VRoid rigs put helper nodes between humanoid bones. It holds:

- `worldFromAvatar`, the conversion from the file's glTF frame into the world frame (see [conventions.md](./conventions.md)), and the rest globals per node in avatar space, which is the pose rendered before any retarget
- per humanoid bone: presence, node, resolved parent, rest world position and rotation, and the rest offset from the parent (the offset a bone keeps whatever rotation it is given)
- derived lengths: upper arm and forearm per side, shoulder width (between the upper-arm joints), hand length (hand joint to middle finger base), and the height above the hips for framing
- per side a `HandRest`: the avatar palm frame in the app's palm convention and a `HandSkeleton` describing the avatar's fingers

The hand rest comes from the shipping hand code rather than a second palm-frame derivation. Fingers are whatever the rig has: a finger's physical bones are its present humanoid slots in order (a Blender-authored rig that maps two bones per finger into the intermediate and distal slots has physical bones 0 and 1 there), and `HandRest::fingerBoneCount` and `fingerSlots` record them. A 21-landmark hand is assembled from the rest joints (wrist = hand node, physical bone i as joint i, the joints the rig lacks down to the fingertip extrapolated along the last bone at 0.8 per step, and a finger with no bones filled with a flat-hand stand-in that keeps it off the output) and run through `HandPoseModel::computePalmFrame` and `computeSkeleton`, with the palmar memory seeded to world down because every VRM rests palms-down in a T-pose. A rig with no middle finger takes +X along the forearm. The chirality `buildFingerJoints` reads from `baseInPalm[Index].y` therefore comes out exactly as for a tracked hand: positive on a left hand, negative on a right, provided the rig's index really sits on the thumb side of its middle finger; a rig whose index and middle are mapped the other way round gets a skeleton warning (shown in the Retarget stage's summary and the log) because its thumb will pronate the wrong way until the mapping is corrected in the rig settings. `neutralDirInPalm` is then overwritten with the avatar's own rest finger directions, an explicit exception to the flat-hand rule for tracked skeletons: zero angles must reproduce the avatar's rest hand, and this skeleton never goes on the wire.

## MToon subset and the renderer

`GlSkinnedMeshRenderer` (`src/Render/GlSkinnedMeshRenderer.h`) draws a model into whatever framebuffer is bound: one VAO per primitive, GPU skinning with four weights per vertex reading joint matrices (`global[joint] * inverseBind`, the mesh node's own transform ignored per the glTF spec) from a `GL_TEXTURE_BUFFER`, since VRoid rigs exceed the 64 matrices GL 3.3 guarantees for a uniform array. Textures upload as `GL_SRGB8_ALPHA8` with mipmaps and a sampler object per glTF texture.

The fragment shader is the MToon 1.0 ramp in linear space: `shading = linearstep(-1 + toony, 1 - toony, NdotL + shift)` and `rgb = mix(shade, base, shading)` with one directional light, a small constant ambient, and gamma encoding on output because the scene framebuffer is plain RGBA8. The material fields read for it:

- `shadeColorFactor`, `shadeMultiplyTexture`, `shadingShiftFactor`, `shadingToonyFactor`
- `renderQueueOffsetNumber` and `transparentWithZWrite`, which order the BLEND draws
- the glTF `alphaMode`, `alphaCutoff` and `doubleSided`

Draw order follows the spec: OPAQUE and MASK, then BLEND with z-write sorted by offset, then BLEND without z-write with depth writes off, sorted by offset. Double-sided materials disable culling and flip the normal on back faces. A material that is not MToon shades as a half-brightness copy of its own base color.

VRM 0.x materials arrive as the `materialProperties` bag and are migrated the way UniVRM and three-vrm do: `_Color` and `_ShadeColor` from gamma to linear, `_MainTex` and `_ShadeTexture` as texture indices, `_ShadeToony` and `_ShadeShift` through the toony and shift remap, `_CullMode` 0 as double-sided, `_ZWrite` into `transparentWithZWrite`, and the Unity `renderQueue` values of the transparent materials ranked into offsets (z-write off onto -9..0 ending at 0, z-write on onto 0..9 starting at 0).

Morph targets deform on the CPU. A primitive with targets keeps its unmorphed vertices and the vertex range its targets touch. When `setMorphWeights` changes any of its weights, that range is recomposed from the base and re-uploaded with `glBufferSubData`. The 3D scene feeds it the shown frame's face profile values through the binding of the same generation (the face below), so the preview shows the face exactly as a receiver holding the same file applies it.

Deferred, tracked in `docs/plan.md`: outline, rim, matcap, UV animation, GPU morphing, spring bones.

## The source pose (`src/Avatar/SourcePose.h`)

`SourcePose` is the hand-off from a pipeline to what poses the avatar: what the pipeline has for this frame, per group (the torso, the head, each arm, each hand), with the frame's clock. It is a plain fixed-size value with no pointers into solver state.

- `pipeline` says which pipeline filled it, which fixes the units and which fields carry values. The position pipeline fills world positions and orientations in meters and the user's proportions. The direct pipeline fills its arm chain in the avatar's units and the placement the bones take.

- `clock` is the filler's: the frame's own timestamp, the time the stateful logic steps on (`stepMs`), the interval since the filler's previous frame (zero on the first frame of an epoch) and a reset epoch that counts the filler's restarts. A consumer that keeps state across frames drops it when the epoch changes and keeps no clock of its own. The output frames' timestamps are not monotonic: a face-only frame is stamped a few milliseconds later than the camera frame that follows it. So the position filler holds `stepMs` at its high-water mark across a backward step of up to `kMaxBackwardStepMs` (500 ms, the size at which the direct solver calls a gap a restart), with an interval of zero, and the holds, the ease and the root follow all step on `stepMs`: no time passes on such a frame, and nothing reads it as a discontinuity. A larger backward step is one: `stepMs` follows the timestamp and the interval is negative. The frame's own timestamp, on the pose and on the wire, is never changed. The direct pipeline never fills from a face-only frame, which repeats the last direct result, so its `stepMs` is its timestamp.

- Each group has a state: measured on this frame, held by the pipeline from an earlier one, or lost. A confidence carries a present flag, so an input that has none is never stored as zero. The position pipeline has the shoulder, forearm, hand and head confidences. The direct pipeline has the hand's and the phone head's, and none for the arm or the torso, whose landmark visibilities are presence scores.

- An arm carries the shoulder, elbow and wrist positions, with the forearm orientation (position) or the chain's directions and the forearm's twist against the avatar's rest palm (direct). A hand carries the world palm (position) or the palm in the measured forearm frame (direct), and the finger angle table with `eFingerZero` naming what an angle of zero means: the captured rest pose (position) or the finger along its metacarpal (direct).

`AvatarRetarget::fillSource` writes it from the inputs the position solve took, and `solve(const SourcePose&, ...)` reads it. The older `solve` signatures run the two in turn. A side tracked with a world anchor is written as measured, and one tracked without is written as lost with its confidence present, which is how the loss stage tells a hand that is seen but cannot be placed, which ends a hold, from one that is not seen, which a hold bridges. `AvatarRetarget::reset` bumps the epoch and the solve clears its root follow on a change. A backward step larger than the clock's limit does not bump it, because the root only snaps on one, so the interval reads negative there.

The direct pipeline is `DirectRetarget::measure`, the loss stage, then `DirectRetarget::place`. `measure` holds every filter, the entry gates, the depth scorer, the lift scale, the palm and finger measurement, the spine limit (the forearm's twist is measured under the limited spine), the earned arm hold and the torso and head holds, and the clock with its restart on a gap or a regression. It writes the source pose and the solve state. `place` turns the source pose into bone rotations and keeps no state: the hips and spine, the head's joint limit and trim, and the arm placement with the wrist limit and the hand and roll trims, for every arm the source carries, a resting one included. The source head is the measured one, before the limit.

## The retarget stage and the loss stage (`src/Avatar/RetargetStage.h`, `LossStage.h`)

`RetargetStage` is the one path from a frame to a posed avatar, for either pipeline: the source fill (`AvatarRetarget::fillSource` or `DirectRetarget::measure`), the loss stage, then the target solve. Its result (`RetargetResult`) holds the source pose after the loss stage, the posed avatar (invalid without a skeleton), the resolved hands for the stream without an avatar, and the direct solve state on a direct frame. The target solve branches on the arm chains' IK weight at its two ends, 1 running the position solve and 0 the direct placement, with the weight fixed by the pipeline.

The loss stage decides what the target solve gets for a group that is not measured. Its policy is data, one `ChainLossPolicy` per group (`LossPolicy`): a minimum confidence, a hold (none, the pipeline's own, or timed), and what follows the hold (release, freeze, or ease to rest over a blend time). The policies come from the project's chain settings (below), resolved per pipeline, and their defaults reproduce what the stream and the direct solver did before the stage existed:

- Position arm: gated on its hand's confidence against `osc.minConfidence`, held for the arm chain's hold length with the confidences decaying linearly to zero, then frozen at the last carried values (`osc.vmcFreezeOnLoss`) or released. A frozen source is solved again every frame, so the root follow keeps moving.

- Position hand: with its arm. Position torso: from the arms. Position head: released at once.

- Direct arm: the hold the solver earned, then the ease into the rig's rest pose over the rig's rest blend. Direct hand: with its arm. Direct torso and head: the solver's hold, then rest.

The stage writes each group's state into the source pose it hands on: measured, held, frozen, resting or lost, with `restBlend` on a resting arm. The direct solver's holds themselves stay in `measure`, because the decision also keeps the chain and its filters alive for the next measurement, and the loss stage passes those held groups through. The loss stage follows the source pose's clock and epoch and keeps no clock of its own.

The vision thread runs the stage in `runOutputStage` on every output frame, ahead of the send-rate limit, hands the result to the streamer and publishes it beside the fused result (`fetchFusedResult`). So the holds, the freeze and the root follow advance on every frame whatever the send rate, and the window shows the pose that is streamed. In direct mode a face-only frame repeats the last direct result. Rig and avatar changes reach the stage through the pending slot (`setAvatarSkeleton`), and only a new skeleton restarts the direct solver, so a rig edit no longer drops a direct arm to rest.

`MainWindow` shows the published pose live. In a replay it runs its own stage through a `RetargetPlayhead`: a step forward within a second of recorded time plays the frames between, and anything else (a scrub, another take, a what-if run) resets the stage and plays the second before the target first, so the holds and filters have state. A scrub lands within about a millimeter of a straight play-through in a position take and within a few degrees in a direct take, whose wrist depth carries several seconds of history. A freeze that began more than a second before a scrub's target is not recovered. On a paused frame only the target solve runs again, so a rig edit that acts there shows at once, and one that acts in the measurement or the loss stage shows on the next frame change.

## The retarget (`src/Avatar/AvatarRetarget.h`)

`AvatarRetarget::solve` poses the avatar from the measured frame. The avatar keeps its own proportions: every bone keeps its rest offset from its humanoid parent and only rotates, so a pose is a root placement plus one world rotation DELTA per bone (`AvatarPose`), measured against the bone's rooted rest rotation. A bone's posed world rotation is `delta * rootRotation * restRotationWorld`, its posed position hangs off its parent's posed position by the parent's delta applied to the rest offset, and an absent bone (`present == false`) sits at identity, following its parent. `computePosedBones` composes that chain and `computePosedGlobals` turns it into node globals for the renderer, where present humanoid bones override their node and every other node (helpers, hair, clothing bones) composes from its parent as authored. The solve is pure over the frame it is given plus one filter state for the root, advanced on frame timestamps, so a replayed recording poses identically.

Per frame, in the world frame:

- Root: with `followShoulders` on and both shoulders tracked, the shoulder line fixes the yaw and the midpoint the translation (the avatar's rest shoulder midpoint lands on the measured one) through a first-order follow with `rootFollowTimeConstantS` (0.3 s), snapping on the first measurement or a timestamp regression. A shoulder dropout holds the last followed placement. Never followed, or follow off, the configured fixed root applies.
- Head: the measured head frame is +X facing, +Y left, +Z up, which is the avatar's rest frame, so the measured orientation is the posed canonical head and the delta is what remains after the root yaw and the head trim: `head * inverse(rootRotation * trim)`.
- Clavicle: with both shoulders measured and the avatar carrying a shoulder bone, swung from rest onto the measured shoulder's direction from the shoulder midpoint, as the measured-length VMC retarget does.
- Wrist target: `avatarShoulder + (userWrist - userShoulder) * (avatarArm / userArm)`, the user's reach scaled onto the avatar's arm (user lengths from `BodyDimensions`, avatar lengths from the skeleton). Without a measured shoulder the avatar's own stands in, which keeps the hand where it was seen. Beyond the avatar's reach the wrist is clamped to it and the arm straightens.
- Elbow: a two-bone solve over the avatar's upper arm and forearm (the circle where the two bone spheres meet), at the point nearest a pole. The pole starts at the rig's elbow hint, `avatarShoulder + rootRotation * elbowHintOffset`. With a measured forearm it moves toward the measured elbow (`getElbowPositionWorld`, scaled the same way) by the arm chain's elbow weight, by default `clamp(forearmConfidence / elbowHintConfidence, 0, 1)`, so a confident forearm decides the bend alone and a fading one hands it back to the hint.
- Upper arm: direction only, a swing from rest. Forearm: direction from the solve, roll from the measured forearm orientation (IMU or body solver) or, with none, from the palm, which puts the wrist at zero bend rather than inventing a twist. The forearm roll trim adds to that roll.
- Hand: the full measured palm frame against the avatar's rest palm frame turned by the hand trim, `restPalm * trim`.
- Fingers: the measured angles scaled by the rig's curl gain (the three bends) and splay gain (lateral), played through `HandPoseModel::buildFingerJoints` on the AVATAR's hand skeleton and its untrimmed posed palm, then each physical bone swung from its rest direction relative to the bone before it, so the hand's roll carries down the chain and zero angles reproduce the avatar's rest hand. A finger with fewer bones than the measured three folds the bends past its last bone into that bone, so a fist still closes on a two-bone finger. Fingers the avatar lacks, and fingers the rig disables, stay absent. An explicit thumb pronation from the rig replaces the one the hand skeleton implies.

One `RetargetStage` solves on the vision thread for the stream and the display alike, and `MainWindow` runs a second only for a replayed frame and the Rest and Demo previews (see the retarget stage below). The vision thread receives the skeleton and the rig settings together through `VisionThread::setAvatarSkeleton`, a pending slot adopted between frames rather than a config refresh, which would end a recording. `makeAvatarRetargetConfig` in `AppConfig.cpp` is the one mapping from the project's avatar settings and the avatar's rig settings to the solver config, which `makeRetargetStageConfig` builds the stage's config from, with the loss policies from the project's chain settings.

## Chain settings (`src/Avatar/RetargetChains.h`)

`RetargetChains` holds the project's settings for each chain the retarget maps: the torso, the head, each arm and each hand. They live in `project.json` under `retarget.chains`, where the rig's corrections live in the avatar's sidecar.

- An arm (`leftArm`, `rightArm`) holds `mapping` (`boneAngles` or `boneAnglesThenIk`), `ikWeight` and `reachScale` (each an `ExprParameter`, a bare number until it has an expression), `goalOffset` (meters, in the rooted torso frame), `elbowWeight` (an `ExprParameter` in 0 to 1, the weight toward the measured elbow) and `loss`.

- The head and the torso hold `loss`. A hand (`leftHand`, `rightHand`) is an empty object: it follows its arm.

- `loss` holds `hold` (`none`, `pipeline` or `timed`), `holdMs`, `after` (`release`, `freeze` or `easeToRest`) and `restBlendMs`. The minimum confidence is not part of it. It stays `osc.minConfidence`.

Loading is tolerant: a missing chain or field, a wrong type or an unknown enum word takes its default, and one warning names them all.

A project without the block runs on a migration (`migrateRetargetChains`): the arms' mapping and weight from the project's shape (IK at weight 1 for a multi-camera project, bone angles at weight 0 for a direct one), the hold from `osc.holdOnDropoutMs` and `osc.vmcFreezeOnLoss` or the pipeline's own hold then ease to rest, the rest blend from the sidecar's `restBlendMs`, and each arm's elbow weight as the function form of the sidecar's elbow hint confidence. An arm block from before the weight, holding `elbowHintConfidence`, migrates the same way on load, and that key is no longer written in the block. Each shape's block keeps the other shape's numbers, so switching the direct mode keeps them. The block is created in memory when an avatar loads into a project without one, or on the first edit of a chain setting, and written by the next project save. Once it exists the two legacy `osc` keys are no longer written and are ignored, while the sidecar keeps reading and writing its `restBlendMs` and `elbowHintConfidence` for other projects and older builds.

`makeRetargetStageConfig` is the one mapping from the config, the rig and the chains to the stage's config, and it resolves the stored block to what each pipeline can do, leaving the stored values alone. The target solve's IK weight is fixed by the pipeline, 1 for position and 0 for direct, whatever the block stores, as is the mapping, which nothing reads yet. The position solve reads each arm's reach scale and goal offset. The wrist goal is the avatar's shoulder plus the measured shoulder-to-wrist offset times a factor, plus the goal offset, then clamped to the avatar's reach. The factor (`reachFactor`) is the avatar-to-user arm length ratio at a reach scale of 1, which scales the user's reach onto the avatar's arm, 1 at a reach scale of 0, which keeps the measured offset in meters, and the linear blend between, with both ends returned exactly so the default is bit-identical. Without a measured shoulder the offset is taken from the avatar's own shoulder, so a reach scale of 0 keeps the hand where it was seen. The measured elbow pole scales by the same factor. The goal offset is in the rooted torso frame (+X facing, +Y the avatar's left, +Z up), carried into the world by the root's rotation as the elbow hint is, and does not move the pole. The goal diagnostic is written after both and before the clamp. The direct pipeline reads neither. For the position pipeline an arm and the head take the stored `none` or `timed` hold with the stored length and the stored `release` or `freeze`, and a `pipeline` hold or an `easeToRest` falls back to the default (a timed hold then freeze for an arm, release at once for the head). For the direct pipeline every chain keeps the solver's hold then ease to rest, and only each arm's rest blend comes from its chain. Each arm's elbow weight comes from its chain.

The elbow weight is the first chain parameter that is a value or a function. Its default is the function form of the rule the solve had: `clamp(source.<side>LowerArm.confidence / T, 0, 1)`, with the threshold `T` printed in the shortest form that reads back as the same float, so the output is unchanged bit for bit until someone writes another function or switches to a plain weight. A threshold of zero or less, where the old rule gave 1 and the language divides by zero to 0, migrates to the plain weight 1. A function reads the `source.*` input table (`src/Avatar/SourcePoseInputs.h`), filled from the source pose after the loss stage: a confidence for `source.head`, `source.leftUpperArm` and `source.rightUpperArm` (the shoulder's), `source.leftLowerArm` and `source.rightLowerArm` (the forearm's) and `source.leftHand` and `source.rightHand`, reading 0 where the pipeline has none, and `.measured` and `.carried` flags for `source.torso`, `source.head`, each `Arm` and each `Hand`. The retarget stage owns one `ExprParameterRunner` per arm and parameter (`ArmParameterEvaluator`, over the elbow weight and the reach scale alike), evaluates them whenever the position solve runs, stepping on the source clock's step time, and hands the solve the weight, so each stage instance keeps its own stateful call sites. Their state resets on a stage reset or a new epoch, and an edit that keeps the text keeps it. `RetargetResult::armParameters` carries per arm and parameter the value the solve took, the raw value before the clamp, and whether the function was in force and compiled. The direct solve never read the threshold and does not read the weight. A replay evaluates the take's chains, so an edit made while a replay is shown changes the field's compile display and not the pose.

An edit replaces the app's immutable chains snapshot (`App::setRetargetChains`) and reaches the vision thread through a pending slot (`VisionThread::setRetargetChains`), which rebuilds the stage's config between frames without a config refresh, so it does not end a recording and keeps the stage's holds and filters. A recording's header and the diagnostic dump carry the chains the take ran on, resolved, and a replay reads them from there. A take from before the block migrates from its own legacy keys and the live rig.

## Rig settings (`src/Avatar/AvatarRig.h`)

Real rigs break the retarget's rest assumptions (a T-pose, palms down, the head facing forward, a human thumb), and some name their bones wrongly. `AvatarRigSettings` holds the corrections. It persists in a sidecar beside the model, `<stem>.mikanrig.json` (`Brendan_VRM.vrm` gets `Brendan_VRM.mikanrig.json`), not in `project.json`, so the corrections travel with the file and every project that loads it shares them. A missing sidecar means defaults. An unreadable one warns and means defaults. The JSON carries a `version`, a `boneNodes` object of overrides, a `rotationTrimDegrees` object holding only the nonzero trims, and a `left` and `right` block of per-side fields.

- Mapping overrides: per humanoid bone, a node NAME (an empty name unmaps the bone), so the sidecar survives a re-export that reorders nodes. `applyRigToModel` rebuilds `humanoidNodes` from `fileHumanoidNodes` plus the overrides. An unknown name warns and keeps the file's mapping. So does unmapping a bone every VRM must have, since the skeleton and the retarget assume those exist. Two bones on one node warns but applies, because that is the normal state halfway through swapping two fingers.

- Rotation trims: Euler degrees (glm's XYZ) rotating the rest frame the retarget matches a measurement against, in that frame's own axes. They exist only where the retarget measures a full frame against an assumed rest: the head (the canonical +X facing, +Y left, +Z up frame), the hands (the palm frame), and the forearms (a single roll, stored in the x component). A trim re-orients what counts as rest. It cannot fix a misassigned bone, and it cannot change the hinge axis the thumb curls about.

- Elbow hint: per arm, a point in the rooted torso frame (+X facing, +Y the avatar's left, +Z up) relative to the avatar's upper-arm joint, default `(-0.15, 0, -0.30)` m, down and back. Living in the torso frame, it turns with the root yaw. `elbowHintConfidence` (default 0.5) is the forearm confidence at which the measured elbow takes over completely. The position solve reads the project's arm chain's elbow weight, whose default function is seeded from this value, and the sidecar's copy stays for other projects. The sidecar also holds the joint limits the direct placement applies: `headLimitDegrees` (70) and `spineLimitDegrees` (45) at the top level and `wristLimitDegrees` (80) per side, each the largest short-arc angle the joint may turn: the head against the neutral head before its trim, the spine against the neutral torso (applied in the measurement, since the forearm's twist is measured under it, and only once a neutral is captured), and the palm in the measured forearm frame. Zero locks the joint at its rest and 180 limits nothing. Only the direct placement applies them, so their sliders show on the Torso, Head and Hand chains of a direct project alone. They are optional fields that an older sidecar loads at those defaults.

- Rest pose: per arm, where the direct retarget eases an arm whose tracking is lost. The rest elbow and the rest wrist are points in the same torso frame as the elbow hint, relative to the upper-arm joint, defaults `(0.05, 0, -0.28)` and `(0.28, 0, -0.34)` m (the upper arm hanging a little forward, the forearm forward and a little down onto a desk), of which only the directions are used, so the pose fits any arm length. The rest palm normal, default `(0, 0, -1)`, is the direction the palm faces (down on the desk), and the rest finger curl (default 15 degrees) bends the four fingers at the base and middle joints, the tip at half, the thumb at the avatar's rest. One rig-wide blend time (default 300 ms, zero snaps) is how long an arm takes to ease into it. The position retarget reads none of these.

- Hand tweaks: per hand, the thumb pronation (automatic, or an explicit signed angle), curl and splay gains (default 1), and five finger enables. The thumb pronation is its own control rather than a trim because it sets the hinge the thumb's MCP and IP bends rotate about. The automatic sign comes from which side of the palm the index sits on (`HandPoseModel::getThumbPronationRad`), which a rig with swapped fingers gets wrong. The override only reaches the avatar retarget: tracking, `computeFingerAngles` and the wire never see it.

`App` owns the settings beside the model and the skeleton. `loadAvatar` reads the sidecar, applies the mapping and builds the skeleton. `setAvatarRig` applies an edit at once. A mapping change reapplies the overrides and rebuilds the skeleton. The model's map is rewritten in place on the main thread, which is safe because only main-thread code reads it and the vision thread holds only the skeleton. Any other edit keeps the skeleton, so the streamer's root follow keeps running while a control is dragged. Every edit goes to the vision thread, and the sidecar is written once edits settle for 3 seconds, on unload, and on shutdown.

## Direct retarget (`src/Avatar/DirectRetarget.h`)

The single-camera direct retarget poses the avatar from one camera's frame with no world calibration. `DirectRetarget::solve` takes that camera's `TrackingFrameResult` (the hand model's wrist pixels and camera-space palm frames, the whole-body observation with its relative depth), the undistorted pinhole (`DirectCameraModel`), the phone head while it streams, the skeleton and a `DirectRetargetConfig`, and emits an `AvatarPose`. It is pure over the frame plus filter and hold state advanced on frame timestamps, so a replayed recording poses identically. The camera is the world (see [conventions.md](./conventions.md)): the root stays at the origin with identity yaw, `Hips` is placed at identity, and the avatar's shoulder width is the scale: the user's head geometry and arm lengths from `BodyConfig` are scaled by the ratio of the avatar's shoulder width to the measured one, so the solver works in the avatar's units with the user's proportions. Every joint of the solved chain sits on the ray through its landmark, and the avatar's bones take the chain's directions, so the posed shoulders reproject onto what the camera saw and the arms point where the user's do, with the avatar's own elbow and wrist landing where its lengths put them. That 2D match reaches a receiver only when its virtual camera has the calibrated field of view and the avatar stands at the measured shoulder depth; over VMC the root is identity today, so a receiver shows the rotations and not the placement.

Per frame:

- Landmarks: usable when provided, with visibility at least 0.5, and inside the frame by 16 px. The model places a joint it cannot see somewhere plausible, so an out-of-frame elbow is treated as unseen. Rays run from the origin through pixels. The wrist has an entry gate for an arm coming from rest: it gets in after 3 consecutive frames at or above the bar, because the model's visibility on a wrist it has placed by guesswork (the hands below the frame, the wrist put beside a hand-shaped thing on the wall) flickers across 0.5, and one frame across it used to pose the arm and start the hold. The bar stays at 0.5: the model scores a plainly visible wrist at 0.5 to 0.7 on the seated takes (p25 0.56 and 0.61 on the two wrists of the first webcam take), so a higher entry bar dropped real hands and cost the seated take 7 degrees of forearm. An arm already placed and within its hold takes the wrist and the hand back the frame they return: a dip of one frame is the model's score wavering on a wrist it has, and the hand's lift is what keeps the wrist's distance from flipping, so a 3-frame re-entry cost the seated take the same.

- Filtering, split by axis: every pixel the solver reads (shoulders, elbows, wrists, nose, ears) goes through a light One Euro band (min cutoff 2.5 Hz, beta 0.1), every depth it derives (the shoulder depth, the ear depth, each wrist's distance along its ray) through a heavy one (0.6 Hz, 0.02), and the palm axes and finger angles through the body solver's direction band (1.5 Hz, 0.08). A landmark unusable this frame resets its filter, so a reacquired joint snaps rather than drags. Every position is a filtered ray times a filtered depth, so pixel noise never becomes a depth jump and a fast move is never lagged by the band that quiets a still one.

- Shoulders: both rays at the depth where they sit the avatar's shoulder width apart (`BodyPoseSolver::depthFromKnownSeparation`), accepted between 0.15 and 2 m, the depth filtered and the shoulders rebuilt on the filtered rays. The torso reads square to the camera: the model's relative depth is too compressed to measure a yaw, and a head-anchored depth moves with a lean. The shoulder line still carries a raised shoulder as roll.

- Elbow and wrist: the wrist pixel is the hand model's wrist while the hand is seen, else the body model's, which keeps the arm placed through a hand dropout. A hand slot is seen only where the body model agrees: the palm detector runs over the whole frame and fires on hand-shaped things in the scene (a framed picture beside the shoulder, on the first webcam takes), while the body model places the wrist by the whole figure and reports one it cannot see as unseen, so a slot farther than half a shoulder width from a seen body wrist, or beside an unseen one, counts as a lost hand for the arm, the palm and the fingers alike. The agreement goes through the same entry gate as the wrist (3 consecutive frames beside a visible wrist, for an arm from rest), so a slot on the scene that the model's wrist brushes past for a frame is not the hand. The camera view draws a slot the solver rejected dimmed (the verdict is `SolveState::Arm::bHandSeen`, handed to the preview panel for the direct camera), with a Hand models stage checkbox that shows every slot in full. The wrist's distance along its ray is the one thing the view does not fix, and it is scored over the distances the arm can reach: between the ray's crossings of the reach sphere about the shoulder, or the one nearest point when the ray misses it, never inside the folded arm's inner sphere. 24 candidates sit evenly across that interval, plus the last frame's distance, and the best is refined by 4 halvings of the spacing around it. Each candidate's elbow holds both of the user's bone lengths by construction: `BodyConfig`'s landmark-space upper arm and forearm through the length ratio, the lengths that make the model's elbow landmark consistent with its shoulder and wrist landmarks. With the avatar's own lengths in their place the surplus or deficit of each bone was consumed by depth, so the elbow reprojected only with the wrist 0.2 m too near on the hands-up pose. While the elbow is seen it sits on the bone circle where the ray's miss (over the 20 px sigma carried to the elbow's distance) and the distance from the previous elbow (over the joint-speed sigma below) sum lowest (`BodyPoseSolver::solveElbowOnBoneCircleNear`): where the ray grazes the circle its nearest point is sharp and wins, and where the ray pierces the circle's plane near its center (a forearm pointing at the camera) every point is about as near the ray, and continuity decides rather than noise. While the elbow is unseen it sits nearest the previous elbow (`solveElbowNearestTo`), or the rig's elbow hint before any chain. The cost is a sum of squared ratios to a sigma each:
	- the elbow's reprojection against its ray, over 20 px, the dominant term while the elbow is seen
	- the move of the wrist along its ray and of the elbow from where it was, each over 2.5 reach per second floored at 0.02 reach, the joint-speed sigma
	- the candidate's shoulder-to-wrist depth against the model's relative depth divided by 0.6 (the compression the gate tool measured), over 0.3 of the reach, a wide prior that decides near-or-far and adds a magnitude where the model offers one
	- while the hand is seen, the candidate's distance against the hand lift's wrist distance (the camera-space palm position through the avatar-to-user length ratio), over 0.15 of that distance, the one metric cue the view has
	- before any chain, with the elbow unseen, half the squared distance the elbow sits from the rig's hint over the reach

	The chosen distance goes through the heavy depth filter, and the elbow is re-solved for the filtered wrist by the same rule.

- The arm's hold is earned: a chain is held across frames without a wrist for as long as its unbroken run of placements lasted plus one frame, up to the 500 ms every group holds, so a wrist the model offered for a few frames leaves the arm up for a few frames rather than half a second, while an arm placed for seconds rides through a dropout of the full hold.

- The hand lift's depth, scored and measured: the lift's wrist distance is also measured against the chain, as a running median over the last 90 samples of the ratio of the geometry's chosen distance to the raw lift distance, so the report shows what the chain makes of the lift. A sample is taken only on a frame where the elbow is seen, reprojects within 20 px, and the arm is under 0.98 of full reach (a straight arm's collapsed bone circle fixes nothing), from a score without the lift term and without the last frame (neither the chain's motion nor the elbow's pull toward where it was), so the sample is this frame's geometry alone against the lift. The scale is bounded to 0.5 to 2 times the avatar-to-user length ratio, which is also its value before any sample, and it resets with the solver. The gate tool reports the scale each take ended on, and the solve state carries the lift's distance both raw and in the avatar's units. The lift's term does not override the elbow's: on the hands-up dump the chain, solved with the avatar's bone lengths, reprojects the elbow within 2 px only at the near crossing, 0.2 m nearer than the lift, and the choice moves 0.02 m toward the lift (plan.md).

- Spine: the torso frame is the shoulder line's frame under a lean, the lean being the shoulder midpoint seen from a pivot one torso length (the rest shoulder midpoint's height above the hips) below the neutral midpoint. Its rotation away from the neutral torso, limited to 45 degrees, lands on `Spine` and is carried as the same world delta onto `Chest`, `UpperChest` and `Neck`, so the arms and the head hang off the leaned torso.

- Head: the phone head wins while it streams, limited to 70 degrees (its orientation is already relative to the anchor the neutral capture set). Otherwise the ears sit at the depth their separation and the head width imply, the nose at the near crossing of its ray with the nose-forward sphere about the ear midpoint, the left and forward vectors are filtered and orthonormalized, and the rotation away from the neutral head is limited to 70 degrees; the ear and nose pixels and the ear depth are filtered as the shoulders are, the left and forward vectors orthonormalized. The rig's head trim applies under either.

- Upper arm and forearm: swings from rest onto the chain's directions, as the position retarget does. The avatar's lengths differ from the user's, so its elbow and wrist do not land on the landmarks, only its shoulders and the directions do.

- Forearm roll and wrist: the measured palm frame (the camera-space palm through the conversion, disambiguated against the forearm, its axes filtered) gives the forearm's twist as the roll of the palm normal about the forearm axis against the avatar's rest palm, and the wrist as the palm in the measured forearm frame (+X along the forearm, +Z the palm normal projected clear of it). The applied roll is the rig's trim plus the twist. The hand bone is the measured wrist, limited to 80 degrees, applied in the avatar's trimmed rest palm under the posed forearm: a straight wrist is the avatar's rest wrist, and the user's hands carry no reference, since a single view's palm at one instant is too unsure to be subtracted from every later frame. A lost hand holds both. The single view cannot tell a hand pointing at the camera from one pointing away, and the hand lift's wrong guess comes back as the palm mirrored along its view ray (the finger and across-palm axes reflected, the normal reflected and negated so the frame stays right-handed). The solver takes whichever of the lifted palm and its mirror has the finger axis continuing the forearm, which the chain fixed before the palm is read. What that rule leaves, a raw palm more than 60 degrees from the filtered one, is held out for a frame as the lift's remaining flip, and a jump that persists two consecutive frames is adopted with the palm filters restarted on it, so a real turn lands a frame late and a one-frame flip never lands.

- Fingers: no zero is captured from the user. `DirectRetarget::measureMonoFingers` reads the hand model's own 3D landmarks through `HandPoseModel::computeMetacarpalFingerAngles`, which measures each finger against its own metacarpal (base minus wrist in the palm plane) so the hand's natural fan is not an angle: a relaxed open hand reads zero lateral on every finger and zero lateral reproduces the avatar's own rest fan, and a spread hand reads its splay. The three bends then lose the bend the hand model reads on a straight finger facing the camera, `kFingerOpenBias` (10, 25 and 16 degrees at the proximal, intermediate and distal joints of the four fingers) and `kThumbOpenBias` (21, 10 and 0.5), and are floored at zero. The bias is the pooled median over both hands of a dump taken with the hands held up open, palms to the camera (`tools/finger_bias.py` prints it from any such dump, the way to re-measure it for a new hand model). Each angle is filtered, then `solveFingerBones`. The solver keeps one palmar-side memory per hand, reset with the hand. A lost hand holds the last angles. The user's fused rest angles (the desk setup's rest capture) are not read: a single view's rest capture is whatever the model made of the hands at that instant, which on a desk pointed at the camera was depth noise, and nothing in the mode could tell.

- Hold and rest: the torso, the head and each arm hold their last solution for 500 ms after the last frame that measured them (an arm for the hold it has earned), then rest. The torso and the head rest at identity. An arm rests at the rig's rest pose: the chain's directions from the rest elbow and wrist offsets, under the lean like a live chain, the palm facing the rest normal through the same hand math as a measured palm (the normal projected clear of the forearm gives the twist and the wrist), the four fingers at the rest curl and the thumb at the avatar's rest. It eases there over the rig's blend time from what its bones took last frame, timed from that frame so the first frame without a chain already moves: the directions and the finger angles mix linearly, the twist goes the shorter way round, the wrist follows the arc, and the time runs through a smoothstep. The chain stays invalid through the ease, so the eased output never feeds the next solve, and a wrist returning mid-ease places its chain the frame the entry gate admits it. After a restart (a frame gap over 500 ms or a timestamp regression) an arm nothing has placed is at rest at once. `valid` stays true throughout, so a receiver is never left with a stale pose. `DirectRetarget::makeRestPose` poses both arms at full rest with the spine straight, what the Retarget stage's Rest preview shows in direct mode and what the tests compare against.

`DirectRetarget::SolveState` (`getSolveState`) is what the last solve measured and chose, filled as the solve runs: the camera model and tilt, the torso's shoulders, midpoint and line frame, the spine and head deltas, and per arm the chain, whether the hand slot and the elbow were seen, the reachable depth interval, the model's depth prior, the lift's distance, the chosen depth with its cost and elbow miss, the filtered depth, the wrist rotation, the twist, the measured and filtered finger angles, and whether the arm is resting and how far into the rest pose it has eased. The pose says where the bones went; the state says why. `makeCameraToWorld` places the camera in the posed avatar's world (the solve's world has the camera at the origin, the avatar's has the root there, so they differ by the measured shoulder midpoint against the posed one), the one placement the dump's overlay, the scene's camera view and the pose report share. The vision thread publishes the state beside the pose (`fetchFusedResult`'s third argument) and the window keeps it, in replay from its own solver.

The neutral capture (`captureNeutral`) stores the current filtered torso frame and shoulder midpoint and the head frame, carried back to the level frame (tilt zero) so a later tilt edit keeps them valid: at solve time the measurements and the references both go to the configured tilt. The tilt itself is the config's slider value, 10 degrees down by default for a webcam on top of the monitor. Nothing estimates it: a torso-axis estimate needs the hips, which the whole-body model places behind a seated user's desk. The vision thread services the capture in `runCalibrationCaptures` and, while the phone streams, sets the face anchor so looking at the screen reads as the identity head on both sources. The hands take no part in it.

`src/Avatar/AvatarRetargetMath.h` holds the helpers both retargets share: `swingTo`, `signedAngle`, `projectPerpendicular`, `wrapAngle`, `swingTwist`, `limitRotationAngle` and `solveFingerBones` (the finger block: gains, the fold into fewer bones, the avatar-hand FK and the per-phalanx swings).

Wiring: `DirectConfig` under the project's `direct` JSON section holds `enabled`, `cameraIndex`, `cameraTiltDegrees` (positive looking down), the neutral present flag and its torso, shoulder midpoint and head (quaternions as `[x, y, z, w]`). `makeDirectRetargetConfig` in `AppConfig.cpp` maps it, the body's shoulder width, head lengths and arm lengths (through `makeBodyDimensions`, so the derived upper arm is the body solver's), and the rig's head trim and per-side fields onto the solver, the one mapping for the vision thread, the window and the gate tool. With direct mode on and the camera present, `VisionThread::runDirectStage` replaces the fusion, IMU and body-solve stages: the output is that camera's result (recorded as a passthrough of that camera, which replay rebuilds from that camera's mirror), the face stage runs as usual, and `solveDirectPose` runs the solver with the camera model from the per-camera intrinsics and the adopted skeleton. The pose goes to `OscStreamer::sendFrame` and is published beside the fused result (`fetchFusedResult`'s second argument); a face-only frame repeats the last pose, and without a skeleton the pose is invalid and the frame streams as before. A skeleton change resets the solver. `MainWindow::updateDisplayAvatar` shows the published pose live and, in replay of a direct-mode recording, runs its own `DirectRetarget` over the recorded camera's frame under the recorded config, reset on a feed switch. The neutral capture is `NeutralCaptureControl` (`src/UI/NeutralCaptureControl.h`), shared by the Direct solver stage and the guided setup's neutral step: a 3 second countdown, then `requestNeutralCapture`, and the landed `VisionThread::NeutralCapture` written into the config as the neutral references under `direct`. Both callers draw the control's status after the capture. The hand wizard does not apply to a direct project (its bones need the desk marker or stereo, and its finger zero is not read), so the hand calibration block replaces its button with a note while direct mode is on. The Direct solver stage holds the switch, the camera, the tilt slider, the capture and its status. The guided setup's single-front variant sets the mode up and captures the neutral as its last step.

## Avatar-driven VMC

With a skeleton set, `OscStreamer` streams the retargeted pose through `VmcRetarget::buildPoseFromAvatar` instead of the measured-length chain: each VMC bone's local rotation is its delta measured against the nearest streamed ancestor's delta (the torso bones `Spine`, `Chest`, `UpperChest` and `Neck` are streamed only when the pose placed them, which the direct retarget does for its lean and the position retarget never does, so an arm hangs off the leaned torso or the rest chest accordingly), and its local position is the avatar's own rest offset from its humanoid parent, so a receiver loading the same file keeps the character's proportions. Bones the pose did not place, or the avatar lacks, are left out and rest on the receiving side. `sendFrame` and `encodeFrame` take the retarget stage's result and only encode it: a valid pose is streamed through the avatar skeleton as it is, and without a skeleton it sends no bones. The root stays identity: the measured-shoulder placement is for the 3D view only, and a whole-body yaw lands in the root rather than the arms, so the streamed arms stay relative to the receiver's own torso. `humanoidBoneForVmc` maps the two Unity-spelled enums by name. Without an avatar the measured-length `VmcRetarget::buildPose` path is unchanged.

The loaded file is announced as `/VMC/Ext/VRM` (path, title, SHA-256) once a second, so a receiver on the same machine can load the very file the bones were retargeted onto and confirm by the hash that it is unchanged. `App::loadAvatar` hands the identity and the face profile binding to the vision thread through `VisionThread::setAvatarIdentity`, adopted between frames like the skeleton.

## The face

The avatar's face is driven by a face profile ([face.md](./face.md)): expressions over the phone and microphone sources, each driving a VRM expression or a morph target. The rig sidecar assigns the avatar its profiles by library id and names the active one. Without one the built-in Auto profile runs, generated from the avatar: its perfect-sync expressions, else its VRM presets plus its ARKit-named morph targets.

`FaceProfileBinding` resolves a profile against the avatar: an expression target by its name in the file (exact, then without case, sent in the file's spelling), a morph target by name on every mesh carrying it or on the one mesh the output names. It is also the receiving half the 3D scene's preview runs: an expression drives its morph binds scaled by the bind weight, a morph target drives its morphs directly, and a morph several targets drive takes the largest weight rather than the sum, so a preset and the ARKit shape it was derived from never double up. The scene applies a frame's values only when the binding's morph count per mesh matches the loaded model's, so a binding built against another model never writes into this one. The preview ignores an expression's `isBinary`, which a receiver applies.

The Profile stage under Face and mouth edits the active profile and shows each binding's live value, and its Edit buttons open a row in the Expression Editor window, whose head close-up preview is the renderer's second consumer: it draws through its own `AvatarMeshView` (a second GPU copy of the model, held only while the editor is open) with the rest pose and the morph weights the binding evaluates for that row alone or for the whole profile.

## Integration

`AvatarConfig` on `AppConfig` persists only the path and placement under the project's `avatar` JSON section: `modelPath` (absolute, or relative to the project folder, then to the exe folder, so `models/avatars/fem_vroid.vrm` names a shipped sample), `showInScene`, `followShoulders`, `rootPosition` and `rootYawDegrees`. The single-camera direct mode's settings live beside it under `direct` (see the Direct retarget section). Loading is never a side effect of reading the config, since replay reconstructs configs headlessly without a GL context. `App` owns the loaded `AvatarModel` and `AvatarSkeleton` as shared pointers with a generation counter; it loads the configured avatar at the end of `activateProject` on the main thread and clears it on the way back to the main menu. `Scene3dPanel` draws the avatar posed by the display retarget (or at rest when no pose is set) before the line pass, with the tracked skeleton lines drawn depth-disabled over it so they stay visible inside the character.

The Avatar panel (`src/UI/AvatarPanel.h`, View menu) loads and unloads a file above four tabs:

- Model: the meta and counts, the avatar's arm lengths against the user's measured ones (the ratio the hand retarget will scale reach by), the rig and skeleton warnings, the sidecar's name, and the placement controls.

- Mapping: a schematic figure (`src/UI/AvatarMapFigure.h`) with Body, Head, Left Hand and Right Hand views and a dot per bone, colored green when mapped, grey when an optional bone is unmapped, red when a required one is, and orange on a warning (one node on two bones, or the index and middle of a hand whose index sits on the far side of the middle from the thumb). Below it, the bones of the shown view, each with a node picker (filtered by the text box, plus an unmapped entry that required bones refuse), a reset to the file's mapping when overridden, and a trim on the head, hands and forearms. Reset all clears every override.

- Retarget: the preview pose (Live, or the canned Rest and Demo frames from `src/Avatar/AvatarPreviewPoses.h`, which pose the scene's avatar so the rig can be tuned without cameras; in direct mode the Rest preview is the direct retarget's rest pose instead, so the rest controls are tuned by eye; the VMC output always follows live tracking), the rest blend time, the elbow hint and its confidence blend and the rest pose per arm, and the hand tweaks per hand.

- Face: the avatar's face profiles, their variables and their VRM expression bindings with live value bars ([face.md](./face.md)).

Each arm's Show gizmo toggle draws its elbow hint in the 3D scene as a camera-facing ring joined to the shoulder. Pressing within 8 pixels of a ring drags it in the camera-facing plane through its starting point, suppressing the orbit drag for that gesture. The dragged world point goes back into the torso-frame offset against the current pose's root rotation and posed upper-arm joint.

- `--test-avatar-retarget`: self test of the retarget and the avatar VMC stream on the shared synthetic rig (`src/Tests/SyntheticAvatar.h`)

- `--render-avatar <file.vrm> [out.png] [yaw] [pitch] [rest|demo]`: renders the rest pose, or the Demo preview frame put through the retarget (`demo`), through the scene renderer from a hidden window into a PNG, with the model's rig sidecar applied, the way to see what the renderer and the retarget produce without driving the UI
